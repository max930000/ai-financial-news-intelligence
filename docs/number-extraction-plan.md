# 新聞數字放大鏡 — 兩人三週執行計畫

負責人:**hw453(AI / 資料分析)**、**yan(全文擷取 / 介面 / 部署)**

## 共同目標

使用者貼上新聞網址,系統擷取全文,找出**營收、淨利、年增率及比較期間**,附上
原文證據;數據足夠時自動驗算。

第一版支援少數選定網站、以繁體中文為主,最後部署到 AWS。擷取失敗時提供貼上
內文的備援,**不繞過付費牆**。

## 為什麼不先寫一套正式規範

不需要另外訂一份形式上的「契約」文件。實際要先講清楚的是兩件具體的事:
**全文擷取會交出哪些資料**、**分析結果怎麼回傳**——這樣兩人各自開發時才接得
起來。這跟「兩人會不會得到不同答案」是兩個問題:格式一致不代表結果一致,
LLM 的結果一致性另外透過模型設定、結果儲存與測試處理,不是靠格式規範解決。

最後部署到 AWS 時,兩人可以用同一套程式和模型設定,不需要為了部署另外维護
第二份邏輯。

## 兩人分工

建議 hw453 負責 AI 與評估,面試時能深入說明模型方法與實驗;yan 負責全文擷取、
介面與部署。

| 工作 | hw453:AI/資料分析 | yan:資料取得/應用 |
|---|---|---|
| 新聞資料 | 設計標註方式、整理標準答案 | 選來源、擷取全文、清理內容 |
| 核心功能 | LLM 擷取、期間辨識、數值驗算 | 網址輸入、文章預覽、結果畫面 |
| 品質檢查 | 證據配對、缺漏判斷、模型評估 | 擷取成功率、內容完整性、錯誤處理 |
| 後端 | 分析函式與分析結果結構 | FastAPI 路由、資料儲存與串接 |
| 上線 | 模型設定、分析耗時與成本紀錄 | AWS 部署、環境設定、日誌 |
| 展示 | 方法比較、成功與失敗案例 | 操作流程、架構與現場 Demo |

兩人都應該走過完整流程一次,也能解釋對方模組的輸入、輸出和限制——不是各自
只顧自己那塊,遇到問題也答不出對方模組發生了什麼事。

## 第 1 週:取得文章,做出第一筆分析

### Day 1:半天對齊(兩人一起決定,不是各自猜)

| 項目 | 第一版決定 |
|---|---|
| 使用者輸入 | 新聞網址;失敗可貼內文 |
| 分析範圍 | 營收、淨利、年增率 |
| 文章資料 | 網址、標題、發布時間、擷取時間、正文、句子 ID |
| 數字紀錄 | 公司、指標、數值、單位/幣別、期間、比較基準、證據句 |
| 缺少資訊 | 留空並說明原因,不補猜 |
| 結果呈現 | 同一篇文章可以有多筆數字紀錄 |
| 驗算容許誤差 | 陳述值與算出值誤差在 ±0.5 個百分點內視為 `consistent`(原文數字通常是四捨五入過的) |
| 擷取失敗判斷標準 | HTTP 失敗、逾時,或正文字數低於 50 字,視為失敗,觸發貼上內文的備援 |

### Day 1 之後:各自開工

- **yan**:選定第一版支援的網站(少數幾個、確認可以合法擷取、不繞過付費牆),
  做出「網址 → 全文 + 句子 ID」的擷取模組
- **hw453**:先用手動蒐集或 yan 初版擷取模組跑出來的文章,設計標註格式,
  開始標註 ground truth,同時著手 LLM 擷取函式的雛形

第 1 週結束的目標:**至少一篇真實文章,從網址輸入到跑出結構化分析結果,
兩人的模組能接起來跑過一次**,不用做到完整、不用做到準,先讓串接跑通。

## 資料結構(兩人開發前先對齊)

### 文章資料(yan 的全文擷取模組輸出,hw453 的分析函式輸入)

```python
class Sentence(BaseModel):
    sentence_id: str
    text: str

class Article(BaseModel):
    url: str
    title: str
    published_at: datetime | None
    fetched_at: datetime
    content: str                # 正文全文
    sentences: list[Sentence]   # 句子切分 + ID,證據句用 sentence_id 指回這裡
```

### 分析結果(hw453 的分析函式輸出,yan 的 API/畫面輸入)

```python
class NumberFact(BaseModel):
    company: str | None
    metric: str                          # 營收、淨利
    value: str | None
    unit: str | None                     # 元、%、億元…
    period: str | None                   # 第二季、2026年8月
    comparison_base: str | None          # 去年同期、上一季
    evidence_sentence_id: str | None     # 對應 Article.sentences 的 ID
    missing_reason: str | None           # 有欄位缺漏時,說明原因,不補猜
    verification: Literal["consistent", "inconsistent", "not_applicable"]
    # 數據足夠時(例如同時有本期與比較期數值),自動驗算陳述的年增率
    # 是否與 (本期-比較期)/比較期 一致;資料不足以驗算就填 not_applicable

class AnalysisResult(BaseModel):
    status: Literal["extracted", "no_target_data", "extraction_failed"]
    facts: list[NumberFact]
    error_message: str | None
```

`status` 三態不可用布林值取代:`extraction_failed` 一定要跟 `no_target_data`
分開,否則系統失敗跟「原文真的沒資料」在評估時分不出來。

## 開發期間的規則

1. 從共同確認的主分支版本各開功能分支
2. 全文擷取、介面、部署由 yan 主責;AI 分析與評估由 hw453 主責
3. 要改雙方都會用到的資料結構(`Article`、`AnalysisResult`)時,先通知對方
4. 做出可執行的小成果就提交 PR,不要等全部完成才第一次整合
